# teamplay-talk 제품 방향 & 설계 결정 (2026-06-26)

## 제품 정체성
- **팀(멀티유저) 의사결정·매니지먼트 AI.** "팀원은 일만, 조율은 AI가."
- 핵심 차별화 = **여러 사람에 걸친 실제 행동**(공유 투표·전원/개인 카톡 알림·정기 리마인더).
  1인용 에이전트(OpenClaw류)가 구조적으로 못 하는 영역.
- 빈 시장: 기존 관리 MCP는 전부 SaaS 래퍼(1인 조작, Linear/Notion을 *이미 써야* 함).
  우린 **"SaaS 없이, 팀이 이미 쓰는 카톡 위에 얹는 그룹 조율."**

## 플랫폼 현실 (중요 제약)
- **PlayMCP = 대회 무대일 뿐.** MCP는 표준이라 클로드·오픈클로 등 어디든 붙음.
  PlayMCP의 유일 가치 = 카카오 유저 배포 + 카카오 1st-party MCP(맵·톡캘린더…) 결합.
- **카카오톡은 단톡(그룹챗)에 제3자 봇 불가** — 공식 Bot API 없음(슬랙/디코/텔레와 다름).
  → 봇이 단톡에 못 들어감. **self-push(나에게 보내기) + PlayMCP 창이 최선.**
  "단톡 네이티브" 비전은 카카오 위에선 구조적으로 불가능.

## 인증 결정
- **자체 OAuth 2.1 서버(카카오 단일) 유지.** PlayMCP broker가 mcpId redirect churn으로
  KOE006 → 자체 서버(고정 콜백)가 해결책. 작동 확인됨(`resolved user=9`).
- **구글 제거.** 2개 OAuth 묶기 = 선례 없음 + 복잡 + 컴플라이언스. Drive는 부차적(나중 별도 MCP).
- 토큰 저장은 **브로드캐스트(남에게 알림) 때문에 불가피** — 서버/구글과 무관.
  대응 = 토큰 암호화 + 개인정보처리방침(국외 보관 고지).

## 핵심 통찰: 투표/폼 시스템 = 모든 것의 기초
역할분배·일정조율·의사결정·진척체크 전부 = **잘 만든 폼/투표 엔진 위의 설정.**
→ 폼 엔진에 투자 = 제품 전체 기초에 투자.
- **자체 구축(외부 X).** 외부(Google Forms=구글, Typeform=데이터 분리)는
  네이티브 통합(방·신원·알림·매칭)을 깸 = 차별화 상실 + 또 다른 auth/컴플라이언스.
- "잘 만든다" = 화려한 UI가 아니라 **탄탄한 데이터모델 + 유연한 질문타입
  (단일/복수/순위/점수/주관식) + 방·신원 연동 + AI가 읽기 좋은 결과.**

## 역할분배 설계
1. 트리거: "○○ 주제로 일 분배해줘"
2. 인원 체크 (room_info)
3. 작업 분해 + 난이도 점수 (**AI 자동 추정** — 팀 조정 UI는 생략, 이의는 챗으로)
4. 균형 묶음: N개 묶음, 난이도 합 ≈ 균등 (+ 주제 응집성). 무거운 주제는 분할 제안.
5. 선호 매칭: 멤버가 묶음 1~N위 → 매칭 (묶음이 다 공평하니 누가 받든 워크로드 공정)
6. 수동 조정 → 확정 → `room_members.role` 기록 + 전원 알림
- 도구 3개: `assign_roles` / `finalize_roles` / `confirm_roles`
- 알고리즘: 작은 팀이라 그리디(LPT)면 충분. 복잡한 거 불필요.

## 로드맵 우선순위
1. **구글 제거**(구조 단순화)
2. **폼/투표 엔진 강화** — 질문타입(순위·점수) 추가, 마감, 멤버 연동, 응답자 추적
3. **역할분배** (엔진 위에 구현)
4. **일정 조율 / 진척 체크** (공통 부품: 서버 스케줄러)
